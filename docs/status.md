## 三、核心阻塞：IDM 跨场景不泛化

判定方式：**训练 3 个屋子录制 → 在留出的 `human-001` 上测**（跨场景，不是同场景随机划分）。

```
ImpalaCNN 从零训练        准确率 45.5%   多数类基线 50.4%   ← 等于瞎猜
冻结 DINOv2 + MLP 头      准确率 45.1%   多数类基线 50.4%   ← 同样等于瞎猜
对照：同场景内随机划分      91.6%（旧回放）                  ← 之前的乐观数字来自这里
```

**但任务本身有信号**（所以不是「不可学」）：

```
                       标签=不动      标签=有动作
旧回放                变化中位 0.33    1.12
录制 house-002        变化中位 0.35    1.30      ← 动作帧变化是 3~4 倍
两分布重叠            74 ~ 78%                  ← 天花板约 70~80%，不是 95%
```

⇒ 瓶颈是**场景多样性/泛化**，不是任务不可学、也不是编码器不够强。

**第三种架构的结论已撤回（2026-09-26），而且房间数也数错了**：

| 架构 | 跨场景留出 | 训练集 |
| --- | --- | --- |
| ImpalaCNN 从零 | 45.5%（基线 50.4%） | 单房间（house×3 会话） |
| 冻结 DINOv2 + MLP 头 | 45.1%（基线 50.4%） | 同上 |
| ~~加差异分支 `trunk(\|a−b\|)`~~ | ~~49.6%（基线 50.4%）~~ | ~~loss → 0.0000~~ |

- **第三行作废，不要引用**：那次运行的日志里明明写着 `epoch 3: 非有限 loss，停止本轮`
  （第 3~7 个 epoch 都有），然后才记下 `loss 0.0000 (最优)`。它是被
  `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 打成 NaN 的运行
  （该变量现已列入 `AGENTS.md` 铁律 4 的禁用项；A/B 实测：设了 epoch 1 起全 NaN，
  不设则 `1.1664 → 0.8827 → 0.7488` 干净收敛）。⇒「差异分支把训练集背到 0 完全过拟合」
  **不成立**，「三种架构都失败」也**不再是三条独立证据**——现在只剩两条，
  而这两条只说明「不比多数类基线好」，**不足以支撑「换架构无用」的强结论**。
- **「4947 对标签、4 个房间」是计数错误**：4947 恰好是三段 `house-001/002/003` 的转移数，
  而这三段是**同一房间的三次会话**（帧间余弦 0.995~0.998）。所以那次跨场景测试的
  **训练集只有 1 个房间**。带标签语料实际的房间结构见第六节。

### 二之六、探索覆盖：二段跳「能表达」≠「数据里有」（2026-09-26）

按住跨步实现后，二段跳仍**几乎不会被随机策略撞上**：
`jump,noop,jump` 的概率是 1/20³ ≈ **0.25%**，3000 步里约 7 次；
`jump,jump`（延长按住）也只有 1/20 ≈ 5%。
**没有数据的动作学不会**——所以「让探索覆盖这些动作序列」是采集阶段的必要环节。

**做法**：`random_rollout` 增加 **motif 探索**（`--motifs`）——从 15 个短动作序列里抽样执行
（`jump×2` / `jump,noop,jump` / `jump,noop,jump,noop,jump` / `right×3` / `right,jump,noop,jump` …），
另一半时间仍是均匀随机。序列仍由 agent 自己派发，**不含任何人类输入**；它是覆盖装置，
与论文「用随机策略采样拓宽 IDM 覆盖」同一性质，不是写死的策略。

**效果（`scripts/measure_jump_height.py`，真机数据）**：

| 会话 | 配置 | 跳跃后的上升高度 |
|---|---|---|
| `selfplay-009-wild`（3000 步） | 均匀随机、一步一松 | 中位 **25 px**，p90 44，**最大 56**，>220 px **0 次** |
| `selfplay-010-motif`（196 步，被中止） | **motif + 按住跨步** | 中位 73，p90 181，**最大 260**，>220 px **3 次（4.3%）** |

⇒ 均匀随机采集出来的数据里**根本没有满高度跳**（最大 56 px），而 motif 版里有 260 px
（只有二段跳/极限长按够得到）。**这就是「先修动作空间再采数据」的必要性证据。**

**顺带修掉一个真阻塞**：`Scene_HardGuide`（提示弹窗）未在确认白名单里，导致采集
**只跑 196 步就被中止**（`aborting random-policy rollout: scene 'Scene_HardGuide' is not
Scene_Map gameplay`）。查游戏源码取证后加入白名单——`Sprite_HardGuide.updateInput` 在
`Input.isAnyTriggered()` 时调 `this.pressOk`，而 `createGuide` 把 `pressOk` 绑到 `popScene`，
`terminate()` 清提示标志：**纯关闭、无条目、无分页**，与 `Scene_ItemObtain` 同规格。

### 二之七、跨区域这道墙：**换目标试过了、换输入格式也试过了，都没动**（2026-09-26）

三个切分、同一个架构、诚实切分（`scripts/probe_displacement_target.py`，修复了一处会把
留出集当训练目标的数据泄漏——它当时已经打印出了两组逐位相同的数字，那是唯一暴露它的信号）：

| 切分 | V1 像素→动作 | V2 像素→Δpx | T 老师数字→动作 |
|---|---|---|---|
| **域内**（训 map4 → 测 map4 另一会话） | **82.7%**（基线 5.8%） | **corr +0.989** | 21.5% |
| **跨区域 A**（map4 → map21） | **3.7%** | corr **−0.034** | 20.1% |
| **跨区域 B**（map21 → map4） | **4.3%** | corr **−0.014** | 22.1% |

⇒ **换目标没有移动墙**；域内两个目标都极好学（0.99 / 82.7%），跨区域一起塌到随机以下。
而**老师的数字跨区域毫不损失**（三段都 20~22%，基线 5.8%）——「位移→动作」是区域无关的，
失败纯在**像素→位移**这一段。

**接着测「是不是模型在读外观」**（`scripts/probe_motion_only_transfer.py`，三臂对照，
训练 6000 对上限、6 epoch，留出 map21）：

| 输入 | 跨区域 dpx corr | 跨区域 dpy corr | 域内 dpx corr |
|---|---|---|---|
| `pair` `[a, b]`（现状） | −0.146 | −0.150 | 0.940 |
| `absdiff` `[\|a−b\|]`（**外观完全去掉**） | −0.083 | −0.019 | **0.970** |
| `sdiff` `[有符号 b−a]`（保留方向） | −0.032 | +0.035 | **0.974** |

**假设被否证**：把外观彻底删掉（纯运动图）**一点也没有改善跨区域**——域内仍然 0.97，
跨区域仍然 ≈0。所以**墙不是输入格式、也不是外观捷径**。

**剩下的解释（与其它实测一致）**：**同一个视觉变化在不同区域的物理含义不同**——
相机是否跟随、地形（斜坡/平台/水）、世界自身是否在动，各区不同。也就是说
「画面变化 → 我的位移」这条映射本身**依赖区域所处的「机制」**，而像素里没有标明当前是哪种机制。
这与之前那条测量吻合：**全局画面变化量与玩家自己的位移相关只有 −0.011**。

⇒ 对最终目标（用视频训练）的含义：**在一个区域训练、去标注另一个区域的画面，目前不成立**，
而且是**自信地错**（相关为负、准确率低于基线）。

### 二之八、**跨区域可以做到——缺的是覆盖，不是配方**（2026-09-26）

三种配方（动作/位移、外观/纯运动、世界/屏幕坐标）在**单区域训练**下跨区域全部归零之后，
补上了一个一直没做的对照：**多个区域一起训、留出其中一个**。

| 训练区域 | 留出 | 目标 | **跨区域 corr_x** | corr_y | 域内 corr_x |
|---|---|---|---|---|---|
| 单一 map 4 | map 21 | world | **−0.083** | −0.019 | 0.970 |
| **4 个区域**（map 4 / 14 / 21 / 22） | **map 8** | world | **+0.712** | +0.167 | 0.944 |
| 同上 | 同上 | screen（相机不变） | 0.070 | 0.105 | 0.480 |

- **世界位移在覆盖到位时跨区域成立（0.712）**，而单区域训练是 −0.083 ⇒
  **之前那道「墙」有一大半是「只在一个区域上训练」造成的，不是配方错误。**
- **相机不变的目标反而更差**（0.070）：世界位移是**物理量**（同一动作在哪都走同样距离），
  屏幕位移被相机行为主导、而相机行为逐区域不同。⇒ **该用的是世界坐标，不是屏幕坐标。**
- 这与人类数据上「房间数扫描」的结论一致：**覆盖换泛化**。

**局限（必须一起引用）**：corr_y 仅 0.167（垂直位移几乎不迁移——下落/地形/平台逐区域差异大）；
留出的 map 8 与训练里的 21/22 同为室外外观相近，可能占了一部分功劳；只留出了一个区域。

### 二之九、速通视频自带按键显示——**可接受的动作标签来源**（2026-09-26）

**决策要点**：B 站那三支才是速通视频；**按键显示算人工数据**，
但「当前路线阻力重重，只能适当取舍」。⇒ 这是一次**已批准的偏差**，必须记录：
用它训练出来的策略**不再是「无人工数据」**，而是「用了视频里的人类按键序列」。

**已下载**（`data/video-src/`，不进 git）：`BV19s4y1y7un` / `BV1Am4y1t7Sv` / `BV13HnzzPEEN`，
均 **1280×720 / 30 fps / 约 43 分钟**（与语料 `fps=4.0` 一致：10293 帧 ≈ 2573 s）。

**面板可读性（实测，`scripts/probe_keycast.py`（**已删除：被 `find_keycast_layout.py` / `find_keycast_cells.py` 取代**））**：面板位于画面左下角（约 x 250-550, y 582-720）。
- **按下 = 亮盘**：亮盘面积 630~830 px、平均亮度 **205~240**，背景 ~55；阈值 >180 + 面积 ≥250
  即可稳定分离（t=600 s 实测同时亮 2 颗＋左侧 1 颗）。
- **平均每帧 1.39 个键亮**（160 帧采样）——符合平台游戏「按住方向 + 偶尔跳跃」的形态。
- 布局已定出 9 个细胞：**左侧是一个十字方向键**（x=37/57/78 一排 + (57,49) 上 + (58,89) 下），
  右侧为按键簇（(134,63)、(129,102)、(167,47)、(203,47)…）。

**已用客观判据钉住方向键（2026-09-26）**：相机跟随角色 ⇒ 「角色向右」让**背景向左移**。
实测（180 s 窗口 / 5400 帧 @30fps，对游戏区做相位相关）：

| 细胞 | 占用率 | 按住时 mean dx | 未按 mean dx | 差 |
|---|---|---|---|---|
| (37,69) | 27% | **+1.80** | −0.41 | **+2.21** |
| (78,69) | 26% | **−1.09** | +0.64 | **−1.72** |
| 其余 6 个 | 1~15% | ≈+0.1 | ≈+0.2 | **≈0** |

⇒ **(78,69)=右**（背景左移、且 80% 时间按住——速通里一直按住右），**(37,69)=左**；
**其余细胞对画面位移无影响 ⇒ 是动作键**（跳跃/攻击），与几何布局（十字方向键＋右侧键簇）一致。
**两条独立证据互相印证**：占用率分布 + 位移符号。

**动作键命名：两条路都试过，都断了（2026-09-26）**

1. **聚合统计判据不成立**。300 s / 9000 帧窗口：10 个细胞里**没有一个**与「亮闪」（攻击/受击特效）
   有意义相关（|r| 全 < 0.08）；而 `|dy|` 指标测的是**相机**（相机两轴都跟随），
   分不出「角色跳起来」与「相机在动」——L 那行 0.83 vs 0.32 是混淆不是因果。**不能据此命名。**
2. **键面上没有字**。最大放大（lanczos 8×）后键帽是**纯灰色圆盘＋金属圈**，无任何字符/图标。

**但拿到了工具的直接证据**：视频简介原文「因为 **KeyDisplay** 配置失败，所以没有显示**十字准线**」
⇒ 控件是 **KeyDisplay**（github.com/xiangCaO233/KeyDisplay）。
其 README 全文只有一句关键信息：**「每个按键可以自由拖动」**
⇒ **布局是使用者自己摆的，没有可查的默认布局**；这也解释了为什么没有标签、
以及「配置失败」会让十字准线不显示。

⇒ 因此「细胞 ↔ 游戏按键」的对应**必须来自外部知识**（使用者/社区约定），
或者改用「跟踪角色本体（而非相机）」的行为判据——后者工作量明显更大，且仍是间接证据。
**当前停在此处等使用者决定。**

**尚未解决（历史记录）**：**动作键各自是什么**（跳跃/攻击/其它），以及是否所有动作键都已被检出
（有些可能极少按下）。判据同样要客观：用角色的竖直运动定跳跃、用攻击特效/敌人受击定攻击。


不能靠猜——打算用**客观判据**定：视频里能同时估出**画面/相机位移**，
于是「哪颗亮键与向右位移同步」就是右键，垂直同理；动作键再用
「出现在角色起跳/攻击的哪一帧」定。**逐帧对得上才算数**。

### 二之十、**这台机器的 Tk 渲染不出任何文字**（2026-09-26 实测）

中文界面「不显示」不是翻译问题，也不是缺字体——**系统装了 Noto Sans CJK**，
但这个 Tk 看不到任何字体：

```
Tk 9.0.4, windowingsystem=x11
tkinter.font.families()      ->  ('fixed',)        只有一个族
font(Noto Sans CJK JP) 解析到 ->  'fixed'
font.measure('中文')          ->  0                ← 宽度为 0，等于什么都不画
xlsfonts                      ->  0 个核心字体
系统 python3 的 Tk             ->  ImportError: libtk8.6.so
```

⇒ **连 ASCII 也是不可见的**（先出现「部分按钮没有文字」，随后「中文不显示」，同一根因），
所以**不要在 Tk 字体配置上继续排障**——没有字体可指。

**处置**：界面改到**浏览器**（本机有 Microsoft Edge）。`scripts/label_keycast_web.py`
起一个本地 HTTP 服务（只绑 127.0.0.1），页面用 `<video>` 原生解码/拖动/变速，
面板放大只是把同一 `<video>` 的局部画进另一块 canvas，标注用 canvas 画——
**中文由浏览器自己的字体栈渲染，必然正常**。细胞判定在页面里用 canvas 取像素做
（只读 300×138 的面板区，很便宜）。

### 二之十一、**真标签监督：第一次超过多数类基线**（2026-09-26）

从速通视频自带的按键显示提取标签之后（见二之九/二之十），IDM 第一次拿到**真值**而不是伪标签。
`scripts/train_keycast_idm.py`，时序切分（前 70% 训练 / 后 30% 留出），6 epoch
（train loss 1.93 → 0.51）：

| 指标 | 数值 | 对照 |
|---|---|---|
| 整体准确率 | **63.5%** | 多数类基线 **56.2%**（**+7.3 点**） |
| macro-recall | **0.308** | 测试集 24 类；伪标签时代恒在 0.09~0.25 |
| **运动帧准确率**（真值≠noop） | **36.3%** | 伪标签时代 0~35%，只答 noop 者为 0 |
| noop 占比 | 真值 56.2% / 预测 53.3% | **没有塌成 noop**（伪标签时代的失败模式） |

**为什么这次可信**：① 监督是真值（视频自带按键显示），不是 IDM 自己的猜测；
② 切分是时序的（随机切分会泄漏近重复邻帧，旧的 91.6% 就是这么来的）；
③ 同时报告运动帧准确率与多数类基线——只答 noop 的模型在这两项上分别得 0 与「=基线」。

**同时做了独立验证**（`label-check` + 画面运动）：按住 `right` 的帧背景平均 dx **−6.27**，
`left` 为 **+6.48**，`noop` 为 **−0.59** —— 符号相反、幅度对称，符合相机跟随模型 ⇒
**方向标签被画面运动这一独立信号验证通过**（不是拿 widget 验 widget）。

**局限（必须一起引用）**：留出集是**同一支视频的后 30%**，仍是同一采集管线；
运动帧准确率 36.3% 在 24 类上（随机 ~4%）虽远高于随机，但离可用策略仍远。

### 二之十二、**跨视频：真标签下依然塌掉**（2026-09-26）

有了**真标签**之后做了两个方向的测量（`scripts/train_keycast_idm.py`）：

| 设置 | 整体准确率 | 多数类基线 | macro-recall | 运动帧准确率 | 预测 noop 占比（真值） |
|---|---|---|---|---|---|
| **同视频**时序留出（前 70% → 后 30%） | **63.5%** | 56.2% | 0.308 | 36.3% | 53.3%（56.2%） |
| **跨视频**（训 视频1 → 测 视频2） | **19.0%** | **30.3%** | 0.051 | 23.8% | **6.6%**（30.3%） |

⇒ **同一支视频内能学到东西（+7.3 点），换一支视频就低于「永远押多数类」**。
两支是**不同播主、不同采集管线、不同阶段区域**——这正是目标场景（要用视频训练），
所以这条结果直接说明：**当前视觉骨干学到的是「这支视频长什么样」，不是「按键→画面变化」**。

另一个细节：跨视频时模型**几乎不再预测 noop（6.6% vs 真值 30.3%）**——它把「不动」也当成动作了，
即类别先验的校准也跟着崩。

**与既有结论的关系**：二之八里「多区域自博弈训练 → 跨区域 corr 0.712」说明**覆盖能换泛化**，
但那是**同一采集管线内**的多区域；这里是**跨采集管线**，覆盖量为每支 1 个域。
⇒ 下一步该做的是（按代价排序）：① 训练时**同时用两支**、对各自留出片段（需要第三支做干净留出则更佳）；
② 换更强视觉骨干；③ 覆盖更多区域。**标签这一侧已经不是瓶颈了**（真值、对齐 +0 帧、独立信号验证通过）。

### 二之十三、第三支视频**方向数据缺失**（2026-09-26 实测）

现象是「第三个视频的方向键不动」，实测确认**不是程序问题**：视频3（`BV1Am4y1t7Sv`）的按键显示里，
左侧那个球的**位置在 300 帧内跨度只有 0.2 px**（x 57.5~57.7、y 65.9~66.2，k=1 组内半径 0.03 px）——
**它从不移动**。对照：视频1 的球有 **9 个离散位置**（k=9 组内半径 0.07 px）。

⇒ 这支视频的 KeyDisplay 配置**没有把方向绑定到那个球上**（球是静态的）。
**直接用它的标签训练会教出「永远不按方向」**，所以「这视频没法用于 IDM 训练」的判断成立。

**但未必完全不可用**，两条路：
1. 看它的**键帽**里是否有若干颗在角色移动时亮起——若有，那四颗就是方向**按键**，
   而我们的动作空间里方向本来就是**按钮**（`left/right/up/down`），所以照样能标注；
2. 若没有，则把视频3 排除在训练之外；跨视频实验退化为两支（训1测2、训2测1），
   或者把它只当作「按钮维度」的第三个域（损失里屏蔽方向位）。

### 二之十四、**键帽字母是「播主的绑定」，不是我们的键位表**（2026-09-26）

新视频 `BV1hc411M7GW` 的按键显示是**带字母的键盘键帽**（比球更好：方向以箭头键帽显示＝直接对应我们的方向按钮）。
但需要指出：**这位播主 `Z=攻击 X=冲刺 C=跳跃`**，而我们的 `config/game.yaml` 是 `Z=跳跃 X=攻击 C=冲刺`。

⇒ **标注的是「动作」，不是「键」**，所以视频本身没问题；但**不能照抄我们键位表去读键帽字母**——
键帽字母只代表**那个人自己的绑定**。这条要写进流程：**每个视频的按键映射都必须单独确认**
（视频1、2 是看画面确认的，所以没踩到；视频4 若按字母照抄就会把跳跃/攻击标反）。

### 二之十五、`BV1hc411M7GW`（键盘式按键显示）：**按下＝变蓝**，且源是可变帧率

这支视频的按键显示**比球的样式更好**（方向以箭头键帽显示、键帽带字母），但有两个必须先解决的问题，
两个都是**我用旧规则/旧假设硬套**造成的：

1. **按下状态是「键帽变蓝」，不是「变亮」**。实测裁图（t=100 时 `C` 键为蓝色、t=330 时 `←` 为蓝色，
   两次面板位置完全一致）：键帽平时是白底黑字，按下后整颗变蓝。而提取器与页面沿用的规则是
   「中心被**亮斑**覆盖」⇒ **对这套键帽不成立**，于是产出 `tapped 85~95%`、不可表达组合 **61.5%**
   （其他视频 6~8%）这类荒唐数字。**上一次提取的标签作废**。
2. **源是可变帧率**：`fps=30` 只得到 106440 帧（应 108000）⇒ 与语料**错位 −207 帧（−51.8 秒）**。
   需要 `-fps_mode cfr`（或按时间戳取样）才能与 4fps 语料对齐。

⇒ **修法**（都还没做）：① 检测规则按「蓝色」判定（B 通道显著高于 R/G），并在细胞文件里加一个样式开关，
页面与提取器都支持；② 提取时强制恒定帧率，语料也重建一次。

### 二之十六、**留一视频交叉验证（3 折）：多视频覆盖也救不了**（2026-09-26）

有 3 支可用视频（视频3 因方向数据缺失排除），做留一视频交叉验证，每折用**两支**训练、留出第三支：

| 折 | 训练 → 测试 | 整体准确率 | 多数类基线 | macro-recall | **运动帧准确率** | 预测 noop（真值） |
|---|---|---|---|---|---|---|
| A | {视频2,视频4} → 视频1 | 36.2% | 37.0% | 0.039 | **0.3%** | 97.5%（37.0%） |
| B | {视频1,视频4} → 视频2 | 26.0% | 30.3% | 0.048 | **9.3%** | 56.5%（30.3%） |
| C | {视频1,视频2} → 视频4 | 51.4% | **77.2%** | 0.039 | **2.4%** | 66.4%（77.2%） |

**三折全部低于多数类基线，运动帧准确率 0.3%~9.3%**（永远答 noop 的模型在运动帧上是 0%）。
第 C 折尤其清楚：留出视频 77.2% 的 tick 是 noop，而模型只拿到 51.4%——**比「什么都不做」还差**。

⇒ **结论：「多加视频」不能解决跨采集管线泛化**。对照二之八那条正结果（**同一管线内**多区域 → 跨区域 corr 0.712）：
**覆盖能在一条管线内换来泛化，跨管线不行**。学到的表征是**「这支视频长什么样」**，不是「按键对画面做了什么」。

⇒ **下一个杠杆是表征，不是数据量**。可选方向（按代价）：
① 数据增强（颜色抖动/随机裁剪/尺度抖动）迫使模型不看采集特性；
② 更强的视觉骨干或**预训练**骨干（当前是小 ImpalaCNN + 随机初始化）；
③ 自监督预训练后再接 IDM（项目已有 SSL 路线可复用）；
④ 换任务形式（例如预测位移/帧间差分而不是 27 类分类）。

**标签侧已经排除嫌疑**：真值、逐帧对齐（+0 / −1 / 0 帧）、方向经画面运动独立验证、动作空间 27 个 mask、
四支视频的映射都经过人工确认。**问题出在视觉表征的跨视频迁移能力上。**

### 二之十七、数据增强对照：**没有改善**（2026-09-26）

同一套 3 折留一视频，训练时加**成对一致**的增强（颜色增益/偏置抖动 + 随机裁剪/缩放，两帧用同一变换）：

| 折 | 对照 整体 / 运动帧 | 加增强 整体 / 运动帧 | 预测 noop（真值） |
|---|---|---|---|
| A | 36.2% / 0.3% | 38.1% / 3.1% | 92.2%（37.0%） |
| B | 26.0% / 9.3% | 30.3% / 0.3% | 98.9%（30.3%） |
| C | 51.4% / 2.4% | **11.6%** / 6.1% | 12.5%（77.2%） |

⇒ **没有一致改善**：两折勉强碰到基线，第三折**大幅变差**（因为它不再押多数类、而其他类又答不对）。
**运动帧准确率仍全部在 0~9%** —— 在真正要紧的指标上与「永远答 noop」无异。

⇒ 至此**数据量**（3 支视频、3.8 万 tick）、**增强**都被排除。剩下的怀疑集中在**目标函数与表征容量**上。
最可疑的一点：**27 类 softmax + 30~77% 的 noop 占比**，使「押多数类」成为最小损失的捷径——
模型的表现（预测 noop 92~99%）正是这个塌缩。**改成「每键二分类（多标签 sigmoid）」可以让每个键独立学习，
从结构上消除这种塌缩**（这是下一步首选，代价也最低）。

### 二之十八、改成「每键二分类」也没用：**三个杠杆全部排除**（2026-09-26）

`scripts/train_keycast_ml.py`：输出头换成每键 sigmoid，损失 BCE，指标换成**每键 macro-F1**
（全空预测得 0 分，所以 F1 无法被"押多数类"伪造）。数据、切分、容量与对照完全相同。

| 折 | 训练 → 测试 | macro-F1 | 逐位准确率 | **ON 位准确率** | 精确匹配 | 预测正例率（真值） |
|---|---|---|---|---|---|---|
| A | {2,4} → 1 | 0.028 | 88.4% | **5.1%** | 30.9% | 2.4%（10.2%） |
| B | {1,4} → 2 | **0.000** | 90.1% | **0.0%** | 29.6% | 0.0%（9.9%） |
| C | {1,2} → 4 | 0.010 | 90.1% | **10.7%** | 12.6% | 7.9%（2.5%） |

⇒ **macro-F1 ≈ 0，ON 位准确率 0~10.7%**；逐位准确率那 88~90% **全部来自预测零**。
换目标函数只是把塌缩换了种写法，**并没有换来可迁移的学习信号**。

**至此三个杠杆全部排除**：① 数据量（3 支视频 / 3.8 万 tick）② 数据增强 ③ 目标函数形式。
结合二之十二（同视频时序留出 63.5% > 基线 56.2%）⇒ **模型能背下一支视频，不能跨视频迁移**。

**剩余候选（都要先登记确认，不要自行开工）**：
1. **更强/预训练的视觉骨干**（仓库已有 DINOv2 嵌入设施；早先「冻结 DINOv2 + MLP 头」在另一套
   设置上得 45.1%，与本任务上的效果未知）；
2. **换任务形式**：预测**帧间差分/位移**而不是按键（已知正面事实：`|a−b|` 直接进 trunk
   在同管线内留出 85.7%）；
3. **自监督预训练**语料后再接 IDM。

### 二之十九、**换预训练骨干：唯一推动数字的杠杆**（2026-09-26）

`scripts/train_keycast_dino.py`：trunk 换成**冻结的 DINOv2 ViT-S/14**（K 用的同一个），
小头吃 `[ea, eb, eb−ea]`，指标与多标签版相同（macro-F1）。特征缓存到 `runs/dino-<stem>.npy`。

| 折 | 小 CNN（随机初始化）F1 / ON位 | **冻结 DINOv2** F1 / ON位 |
|---|---|---|
| A `{2,4}→1` | 0.028 / 5.1% | **0.130 / 16.0%** |
| B `{1,4}→2` | 0.000 / 0.0% | **0.173 / 31.8%** |
| C `{1,2}→4` | 0.010 / 10.7% | 0.032 / 9.9% |

⇒ **两折明显改善、一折持平**：0.028→0.130、0.000→0.173（ON 位 0%→31.8%）。
对照另外三个杠杆（数据量、增强、目标函数）**全都不动**，这条**动了** ⇒ **支持「瓶颈是表征」这一诊断**。
但 **macro-F1 0.03~0.17 仍远不可用**（ON 位 10~32%，随机水平约 10%）。

**结论（四条负面→一条方向性正面）**：数据/增强/目标函数都不是关键，**表征是**；
但仅靠「换一个冻结的现成骨干」还不够。后续若要继续，方向应是
① 更大/可微调的骨干（ViT-B、或在本语料上微调 ViT-S）；② 与「预测帧间差分/位移」的任务形式结合
（已知 `|a−b|` 进 trunk 在同管线内 85.7%）；③ 自监督预训练。**均需先定，不要自行开工。**

### 二之二十、微调骨干：**一个 epoch 不够，而且这次还不如冻结**（2026-09-26）

`scripts/train_keycast_vit.py`：同一套三折，把冻结的 ViT-S 换成**可微调**（112²、AdamW trunk 2e-4 / head 1e-3、
1 epoch——预算内的最小配置）。

| 配置 | B 折（{1,4}→2）macro-F1 | ON 位准确率 | 预测正例率（真值 9.9%） |
|---|---|---|---|
| 小 CNN（随机初始化） | 0.000 | 0.0% | 0.0% |
| **冻结 DINOv2** | **0.173** | 31.8% | 7.1% |
| 微调 DINOv2（1 epoch） | **0.008** | 1.4% | 0.3% |

⇒ **微调这一版不如冻结**（0.008 vs 0.173），且塌缩成「几乎不预测任何键」。

**但不能据此否定「微调」这条路**：单支训练视频的冒烟运行里，**方向键确实被学出来了**——
`left` F1 **0.317**（P 0.234 / R 0.489）、`right` F1 **0.170**，而冻结版这两项全是 0。
⇒ 说明**可微调的骨干有能力学到这些键**，但它**在配置之间极不稳定**；本轮的 1 epoch、
无学习率调度、112²、trunk 2e-4 显然不是一个公平的微调配方。

**诚实的边界**：这次比对只回答「**一个便宜的 epoch 能买到什么**」（答案：买不到），
**不回答「好好微调能不能行」**。后者需要：更低的学习率 + 先冻后解冻的调度 + 更多 epoch +
单折调参，**算力远超本会话预算**。

### 二之二十一、换任务形式（帧间差分）**也没有用**——六个杠杆的最终账（2026-09-26）

在冻结 DINOv2 特征上把组合从 `[ea,eb,eb−ea]` 换成 `[ea,eb,|ea−eb|]`（`absdiff`）与两者都上（`both`），
同一套三折、同一头、同一指标：

| 折 | `cat`（基线） | `absdiff` | `both` |
|---|---|---|---|
| A | 0.130 | ~0.117 | 0.130 |
| B | 0.173 | 0.165 | 0.159 |
| C | 0.032 | 0.032 | 0.029 |

⇒ **差异在噪声范围内**。注意这与「`|a−b|` 进 trunk 得 85.7%」那条旧事实**不矛盾**：那条是
**同一管线内**的二分类「动没动」，而这里要的是**跨视频判出按了哪个键**——**「动了」≠「按了哪个键」**
（AGENTS.md 第 5 条早就写了这句）。

**六个杠杆的最终账**：

| 杠杆 | 结论 |
|---|---|
| 标签质量（真值/对齐/方向验证） | 已排除嫌疑 |
| 数据量（3 支视频、3.8 万 tick） | **不动** |
| 数据增强（成对一致） | **不动** |
| 目标函数（softmax → 每键多标签） | **不动** |
| 任务形式（差分特征） | **不动** |
| **预训练骨干（冻结 DINOv2）** | **唯一推动**：macro-F1 0.000→0.173、ON 位 0%→33% |
| 微调骨干（1 cheap epoch） | 不如冻结（0.008），但**冒烟运行里方向键 F1 达 0.317** ⇒ 骨干有能力，只是配方不对 |

⇒ **诊断确认：瓶颈在视觉表征**；且**最有效的下一步是「正经的微调配方」**（低 lr + 先冻后解冻 +
多 epoch + 单折调参），代价是**超出本会话预算的算力**。截至此处，冻结 DINOv2 的
**macro-F1 0.13~0.17** 是所有配置中的最好结果，**仍远不可用**。

### 二之二十二、正经微调配方：**单项最好，但整体仍偏斜**（2026-09-26）

改用低 trunk lr（**1e-5**）+ **先冻后解冻**（前 30% 步只训头，实测 step 459 解冻）+ 余弦退火 + 2 epoch，
跑 B 折（{1,4}→2）：

| 指标 | 冻结 DINOv2 | 微调（trunk 2e-4、1 epoch） | **微调（正经配方）** |
|---|---|---|---|

### 二之三十、角色细节假说也被否证：**方向的证据来自背景整体滚动**（2026-09-26）

一处合理怀疑：32×32 下角色只有亚像素（原始 1280×720 里约 30 px → 语料 256² 约 6 px → 32×32 约 0.75 px），
**角色朝向（区分左右的关键）根本看不见**，这或许就是学不会的原因。

实测（视频1，同一探针，同一 32×32 特征维数，只改裁剪范围）：

| 输入 | 左/右 acc | 随机 | 每块原生 px |
|---|---|---|---|
| **语料 256²（整帧）** | **0.637** | 0.537 | 8 |
| 400² 中心裁剪 | 0.517 | 0.537 | 12.5 |
| 160² 近角色裁剪 | 0.530 | 0.537 | 5.0 |

⇒ **裁到角色附近反而降到随机**；**整帧最好**。
**机理**：左右方向的证据来自**背景整体滚动**（相机跟随角色 ⇒ 大尺度运动），
角色自身姿态变化很小、且相机并不总把角色置于中心。
⇒ ① 「角色看不清」**不是**瓶颈；② 大尺度运动**低分辨率也能读到**——这正好解释
二之二十九里「32×32 优于 64×64」；③ **语料用 256² 整帧是正确的选择**。

**排除清单增至十二条**：… / 更长窗口 / 更高分辨率 / **角色细节裁剪**。

**剩下的判断**：本任务的可用证据主要是**全局运动方向**（弱但真实，0.637），
而 **9 个键的状态**要求从同一份证据里分辨出「哪一个键」，这正是缺的那一环。

### 二之三十一、事件表述也被否证：同形的问题并没更容易（2026-09-26）

`scripts/probe_key_events.py`：同一批特征（`|f_t − f_{t-1}|` 下采样 32×32）、同一样本、同一线性探针，
只把问题从「按住哪些键（状态）」换成「**这一 tick 哪个键跳变了（事件）**」：

| 视频 | 目标 | macro-F1 | ON 位 | 正例率 |
|---|---|---|---|---|
| BV13HnzzPEEN | **EVENT** | 0.153 | 0.300 | 8.5% |
| BV13HnzzPEEN | state | **0.267** | 0.369 | 11.9% |
| BV19s4y1y7un | **EVENT** | 0.169 | 0.304 | 6.5% |
| BV19s4y1y7un | state | **0.208** | 0.301 | 9.2% |

⇒ **事件表述没有更好，反而更差**（更稀疏）。「让问题与证据同形」这个思路**被否证**。
注意 ON 位对事件仍有 0.30——**当事件发生时画面确实显示了「有变化」，但读不出「是哪个键」**。

**本会话最可靠的一句话**：帧间差分能告诉你「**有东西动了**」，弱地告诉你「**朝哪个方向动了**」（0.575~0.637），
但**读不出「是哪个键」**——这一点在**状态与事件两种表述、多种分辨率与窗口、多种表征**下都成立。

### 二之三十二、分辨率假说也被否证 ⇒ **十四条排除，天花板是任务性质**（2026-09-26）

最后一条未被测过的路径：**语料分辨率太低（角色仅 6 px）会不会把动作键的局部动画抹掉**。
建了一份 512×288 灰度语料（角色 ~12 px，细节 2 倍），用**同一把线性探针**对比：

| 输入 | 特征网格 | macro-F1 | ON 位 |
|---|---|---|---|
| 256² 语料（角色 ~6 px） | 32×32 | 0.191 | 0.283 |
| **512×288（角色 ~12 px）** | 32×32 | **0.197** | **0.297** |
| 512×288 | 64×64 | 0.171 | 0.234 |

⇒ **细节翻倍只动了 0.006 / 0.014（噪声量级）**；R=64 依旧更差（粗特征反而更能读大尺度运动，与二之二十九一致）。
（另：同数据上小 CNN 一臂两分辨率都塌成全零 ⇒ 该对比不可判，故改用已验证的线性探针。）

**⇒ 至此十四条排除，且每条都对应一个可复现的测量**：
标签质量 / 数据量 / 增强 / 目标函数 / 池化差分 / 预训练骨干 / 微调 / 配平 / `|a−b|` 进卷积 /
更长窗口 / 更高特征分辨率 / 角色细节裁剪 / **事件表述** / **更高语料分辨率**。

**唯一可用的信号**：全局背景滚动 → 方向（二分类 0.637）；
**天花板**：9 键状态/事件 ≈ **0.19~0.27 macro-F1、ON 位 ~0.30**，在**所有**上述配置下不变。

⇒ **天花板是「4 fps 下的单帧对里，关于『哪个键』的信息本来就只到这个程度」这一任务性质，
而不是管线缺陷。** 若要突破，必须改变**信息来源**（例如训练期用引擎状态当老师），
而那就**不是**本会话所验证的「从视频学」这条路了。

> **本节 二之九 ~ 二之三十二 的路线已于 2026-09-26 收口**，交接文档见 `docs/keycast-handover.md`
> （一页结论 + 14 条排除各自的复现命令 + 数据清单 + 踩坑清单）。**继续之前先读它。**

### 二之三十三、**重大修正：未来窗把动作键从 0.126 抬到 0.678**（2026-09-26，用户提出的方向）

**前提修正（用户指出，我先前搞错了）**：ASH 里 IDM 是**在自博弈轨迹上训练**（动作已知），
然后**被应用到语料视频**去产伪动作（`bootstrap.py` 里 `chunks.append(idm(a, b))` 明确注释
「for a 13419-frame video」）。**它的推理目标是录像 ⇒ 未来帧本来就可见、可以合法使用** ✓
必须保持因果的只有 **π**，而 π 吃的是观测、不是 IDM 的窗口。

**动机**：按键的证据是它的**后果**（跳跃弧线、挥击、冲刺特效），而后果**发生在按键之后**；
我们的语料是 4 fps、一对帧只覆盖 0.25 s，**恰好把后果截断**；且二之二十九的 K 扫描**只回看过去**。

**实测**（视频1，30 fps 帧库，线性探针，时序切分，16×16/帧）：

| 时间窗 | macro-F1 | ON 位 | **动作键均值** | left | right |
|---|---|---|---|---|---|
| 只有当前帧 | 0.205 | 0.237 | **0.126** | 0.56 | 0.64 |
| 过去 8 帧 → 当前 | 0.246 | 0.267 | **0.195** | 0.51 | 0.61 |
| **当前 → 未来 8 帧** | **0.578** | **0.654** | **0.678** | 0.68 | **0.90** |
| 过去 8 + 未来 8（17 帧） | 0.497 | 0.562 | 0.598 | 0.57 | 0.90 |
| 过去 16 + 未来 16（33 帧） | 0.438 | 0.487 | 0.505 | 0.53 | 0.85 |

⇒ ① **只用未来最好**（macro-F1 **0.578**、动作键 **0.678**）；② **加过去反而更差**（0.497），
**窗口越长越差**（0.438）——与「后果才是证据、多余上下文只是噪声/过拟合」一致。

**⇒ 本节前 24 节「天花板 ≈0.2」的结论必须限定为：那是「因果/只看过去 + 4 fps 单对帧」表述下的天花板，
不是任务本身的天花板。** 我先前把所有失败归因于「信息量不足」，**方向搞错了**。

**尚未验证（下一道门）**：
1. **跨视频**是否成立（本结果是同视频内线性探针；跨视频是本项目的真正门槛）；
2. 0.27 s 是否最优（8 帧是一个未调的选择；推测应与动作时长匹配，可扫 ±4/6/8/12）；
3. 该表述**必须配 30 fps 帧库** ⇒ 计算量显著上升，**这正是算力（与更多数据）会买到东西的地方**。

### 二之三十四、未来窗长度扫描：**峰值在 0.27 s，与动作时长吻合**（2026-09-26）

同一探针（视频1，30 fps，16×16/帧，时序切分），只改未来窗长度：

| 窗口 | macro-F1 | **动作键均值** |
|---|---|---|
| 只有当前帧 (0.00 s) | 0.197 | 0.108 |
| + 未来 4 帧 (0.13 s) | 0.359 | 0.333 |
| **+ 未来 8 帧 (0.27 s)** | **0.594** | **0.681** |
| + 未来 12 帧 (0.40 s) | 0.539 | 0.656 |
| + 未来 15 帧 (0.50 s) | 0.529 | 0.646 |
| + 未来 20 帧 (0.67 s) | 0.486 | 0.603 |

⇒ **单峰曲线，峰值 0.27 s** —— 与**动作动画的时长**（跳跃弧线/挥击约 0.25~0.3 s）吻合，
说明这不是调参巧合而是**证据本身的时间尺度**：超出后只是**下一段动作与场景运动**的噪声。

**工程含义**：窗口取 **0.27~0.4 s（8~12 帧 @30fps）** 最优；0.5 s（15 帧）仅低 ~0.06，仍在可用范围，
若动作时长不一，**略宽的窗口更鲁棒**。

### 二之三十五、彩色 vs 灰度 + 空间细节：**灰度更好、细节越细越好**（2026-09-26）

同一探针（视频1，窗口 = 当前+未来 8 帧 @30fps，时序切分）：

| 输入 | 维数 | macro-F1 | **动作键均值** |
|---|---|---|---|
| 灰度 16×16 | 2304 | 0.594 | 0.681 |
| 灰度 24×24 | 5184 | 0.683 | 0.745 |
| **灰度 32×32** | 9216 | **0.730** | **0.855** |
| **彩色 16×16×3** | 6912 | **0.499** | 0.610 |

⇒ ① **彩色明显更差**（灰度 24²=0.683@5184 维 vs 彩色 16²=0.499@6912 维）：
多出的两个色度通道是**浪费的维度**，而有用信号（运动/亮度变化）本来就在灰度里；
**「大招黄条/冲刺蓝色特效」这些颜色线索没有兑现**（意外，但数据如此）。
② **空间细节显著有用**：16²→32² 让 macro-F1 0.594→0.730、动作键 0.681→**0.855**。
（与二之二十九「32 优于 64」不矛盾：那次是**因果差分图**在 **256² 语料**上的块大小，
这次是**未来窗的帧**在 96² 库上的网格——**未来窗里，细节越细越好**。）

**当前最优配方（同视频内线性探针）**：**灰度 + 未来窗 0.27 s + 网格 32²** ⇒
**macro-F1 0.730、动作键 0.855**（对比：因果单帧对 0.197/0.108）。趋势未饱和，48²/64² 值得再扫。

### 二之三、潜在动作模型（LAM）路线：本探针**不下结论**（2026-09-26）

曾提出 LAM 家族（Genie / LAPO / CLAM）——从视频无监督发现潜在动作、不需要动作标签，
这正对上「训练期无人类数据 + 可参考视频」。判断与做法写在 `scripts/probe_latent_action.py`：
**LAM 绕过的是「标签不可辨识」，绕不过「因果不可辨识」**（从像素上看不出「世界在动」
还是「我在动」——我们实测过：不动时画面变化最大 0.0998，走路只有 0.0039；
「画面变化量→玩家位移」相关 −0.011）。

探针按三个判据设计（老师当裁判）：①动作对齐 ②**混淆测试**（玩家没动/世界在动的转移上
latent 是否恒定，生死线）③跨会话一致。**但本次运行没有拿到判决**：

```
训练：只用「画面真的变了」的 1239 对（3500 对里的 35.4%）
变化图 MSE：0.00480 → 0.00467（第 1 个 epoch）→ 之后 11 个 epoch 完全不动
z 使用量对照：真码 0.00186 | 打乱码 0.00186 | **打乱后差 +0.0%**
⇒ 解码器根本没在用 latent，它只输出了「平均变化图」这一个常数。
```

**这不是「LAM 在这份数据上不行」的证据，而是这个探针失败的证据**，理由是我们自己的
受控实验：同一批数据的像素对**可以**预测玩家位移（corr 0.92）——信息是存在的。
所以问题在这个玩具模型（64×64、16 码、~0.1M 参数、1239 对训练、无感知损失、
MSE 被大量零像素主导），不是在数据。**已把该对照做成硬闸**：对照不通过就拒绝输出判据，
不允许把「模型没训起来」包装成路线结论。

**真正关于可行性的定量事实（这些是可以说的）**：
- 一个区域内每 3500 步自博弈只产出约 **1239 个「画面真的变了」的对**——对无监督发现来说极少；
- LAPO/CLAM 依赖**可控性覆盖**（同一状态附近出现多种后果），而**速通录像是最坏情况**
  （专家不失败、不走回头路、状态分布是窄管）——我们允许的参考视频正是这一类；
- 量级差：Genie 是 11B 参数 / 20 万小时视频，我们的语料是 6 个速通录像 / 68440 帧 ≈ 4.75 小时。

**结论**：LAM 路线**未被否证，但也未被支持**；要继续只有两条现实路径——先扩自博弈覆盖
（同一批数据也是已知有效的那条监督路线的燃料），或换成正经的 VQ-VAE/LAM 实现，
再用这三个判据去判（判据本身已经写好且正确）。

### 二之四、**第一个可用结果**：按「动作意图一致性」筛选后，像素→动作 65.9%（2026-09-26）

判据（`data/effect.py`）：**动作是否真的把玩家推向它想要的方向、且位移 ≥2px**。
三态——有效 / 无效 / 无法判定（无位移意图的动作，如 noop/attack/item，位移判不了它们）。

真机实测的构成比例：**可判定的转移里约 57% 有效**，地点无关（室内 57.0% vs 室外起采 58.1%）
——那 43% 的浪费**是随机策略自己造成的**（顶墙 / 自我抵消），不是地形造成的。

**实验（会话级切分：用 002+003 训，留出完整会话 004 评；评估集 = 留出会话里意图一致的 1027 对）**：

| 臂 | 训练对数 | 准确率 | macro-recall（随机 0.083） |
|---|---|---|---|
| A 全部转移 | 3500 | 56.1% | 0.527 |
| **B 只喂意图一致** | **1198** | **65.9%** | **0.641** |
| C 随机等量（同 1198 对） | 1198 | 34.9% | 0.356 |

- **B 用 A 的 1/3 数据反超 10 个百分点**，比同量随机子集高 **31 个百分点**
  ⇒ **组成 > 数量**这条在合规数据源上再次成立，而且是同一批数据、同一个判据。
- 65.9% / macro-recall 0.641 是在**留出的完整会话**上得到的（不是同会话时间切分）。
- 对照此前人类数据上的最好数字：45~53%（基线 50%）；**这次是 65.9%，基线 6.2%**。

**未测（必须一起引用）**：
- 评估集只含「意图一致」的对（这正是要给视频打标签时该用的子集），**在未筛选的留出集上没测**；
- **跨区域/跨场景泛化仍未测**——留出会话和训练会话在同一个区域、同一个策略下采集；
- 有效样本仍然很少（1198 对）；4 个动作类（noop/attack/dash/item 等无位移意图的）在这套判据下
  从未被评估过。

### 二之五、自博弈 + 引擎老师：第一个明确的正结果，以及真正的过滤器（2026-09-26）

目标已明确：**纯视觉速通模型、训练期无人类数据、可用视频、引擎状态允许当训练期老师**。
因此自博弈（agent 自己的动作 = 真标签）是唯一允许的动作信号来源。第一批合规数据
`runs/selfplay/selfplay-002.npz`：3000 步随机策略（map 4 小屋，362 s 墙钟，128px）。

**老师的语义先在真机上验证过**（`scripts/probe_telemetry_semantics.py`，每个动作 5 次、
每次按住 15 帧 = 一个控制间隔）：

| 动作 | physics Δpx | physics Δpy | 画面变化 |
|---|---|---|---|
| noop | 0.0 | **+96.0** | **0.0998** ← 最大 |
| left | **−87.0** | 0.0 | 0.0039 |
| right | **+87.0** | 0.0 | 0.0038 |
| jump | 0.0 | **−131.0** | 0.1002 |

⇒ 老师**精确可分**（∓87，5/5）；而**画面变化量是反序的**——什么都不按时变化最大（重力），
真的在走路时最小（室内只有小精灵在不动背景上平移）。**本项目用过的所有「静止画面」启发式
在这里对「走路」都是盲的。**

**目标对比（同一批数据、时间序 70/30 切分，lr 3e-4 从零训 8 epoch）**：

| | 结果 |
|---|---|
| **V2 像素 → 玩家位移 (Δpx, Δpy)** | Δpx：skill **+0.786**、corr **+0.922**；Δpy：skill **+0.853**、corr **+0.933** |
| V1 像素 → 20 类动作（旧目标） | 准确率 **28.7%**（基线 6.2%）| macro-recall 0.286（随机 0.05）|
| T 老师数字 → 动作 | 准确率 17.4%（基线 6.2%）| macro-recall 0.186 |

**两个对照排除了平凡解释**：持久性预测 Δ_t=Δ_{t-1} 的 skill 是**负的**（−0.180 / −0.809，
corr 0.41 / 0.09），所以自相关解释不了 0.92；而**「画面变化量 → 位移」的相关是 −0.011 / +0.016**
——全局运动统计对玩家自己的位移**零相关**。

**但真正的发现是过滤器该长什么样**：按「动作是否真的把它推向想去的方向、且位移 ≥2px」判，
3000 步里**只有 19.3% 方向一致**，其余 80.7% 是顶墙/被地形抵消/重力主导
（例：`right, jump` 一致率 **0.0%**，其 Δpx 均值 **−0.3**）。
⇒ 而 `data/effect.py` 现在的判据（`own_moved`）在这批上给的是 **83.3%**——**它把重力下落
也算成了「人在动」，太宽松**。正确的判据是**动作意图一致性**，它需要动作本身参与判断。

⇒ 这条同时解释了整条历史：伪标签器的训练数据里约 80% 的对「动作没有效果」，所以它只能答先验。
**它不是学到了错的东西，而是训练集里那些对本身教不了东西。**

**未做**：还没用「方向一致」的子集重训（子集只有 ~580 对）；也还没测跨区域泛化。
V1 的 28.7% 虽然高于基线，但**离能拿来给视频打伪标签还差很远**。

### 三之零、「换配重」能救吗：能改善，但救不了（2026-09-26）

既然只有一小部分对是可辨识的，那**只喂可辨识的对**会怎样？四臂对照，都在**留出组里有信息的运动帧**上评
（该留出集全是运动帧，答 noop 必然全错），7 折平均（`scripts/probe_informative_subset.py`）：

| 臂 | 训练对数 | 准确率 | **macro-recall** | 预测 noop |
|---|---|---|---|---|
| A 全量（= 现在的做法） | 25184 | 29.6% | **0.112** | 50.8% |
| **B 只喂可辨识对** | 2410 | 39.4% | **0.177** | 0.0% |
| C 随机等量（同 2410 对，随机抽） | 2410 | 4.8% | **0.018** | 87.6% |
| D 可辨识对 + 等量静止 noop | 4820 | 21.3% | 0.089 | 65.2% |

（随机水平 ≈ 0.135）

- **B > C 且 C ≈ 0**：同样 2410 对，**组成**决定成败——随机抽的那份全是先验，模型退化成只会答 noop。
- **B > A 且 B 只用 A 的 1/10 数据**：多喂数据不但没用，还更差（A 在随机水平）。
- **D < B**：把「静止且真没按键」的对拉回来配平，反而退回去——那些对在教「别动」。

⇒ **配重确实是杠杆，方向也印证了可辨识性分析**；但**绝对水平仍然不可用**
（0.177 vs 随机 0.135；单折最好 0.310，而那一折留出只有 151 对）。
**结论：修配重能让指标动，但动不到能用。** 剩下的差距正是「**画面在动 — 是世界在动还是我在动**」，
而那正是引擎状态可以免费消掉的一项。

**本节的局限（必须一起引用）**：判定「可辨识」的阈值在训练集上选出，7 折间在 **0.018~0.045** 之间漂，
对应的可辨识比例是 **4.5%~11.6%**（不是第一节那个 22.2%——那个数是另一阈值下的）；留出有信息的对只有
**7~747 对**，其中 2 折只有 7 和 38 对，噪声很大，也计入了均值。

### 三之一、标签可辨识性：为什么它只能答先验（2026-09-26，修正后所测）

曾提议「把 noop 占比高的片段当垃圾数据清掉」——**这个前提是错的，已修正**：
那些静态帧是**正确行为**（等剧情文本走完、运动平台载着走），不是垃圾。

但它揭示了一个更根本的问题：**「画面 → 按键」这个逆问题在这些数据上不是函数**。

| | 标签=不动 | 标签=有动作 |
|---|---|---|
| **画面没变** | **42.7%**（等剧情/平台/纯待机） | **10.3%**（顶着墙按方向） |
| **画面变了** | **24.8%**（平台或过场把画面带走） | **22.2%**（正常按键） |

实测（`scripts/probe_label_identifiability.py`，全语料 29381 对，阈值取对模型最有利的那个）：

```
画面变化量区分「有动作 vs 不动」的 AUC = 0.690     ← 1.0 完美，0.5 瞎猜
不可辨识对 = 35.0%                                ← 两种成因之和
```

**只有 22.2% 的对是「干净且能教东西」的**；**42.7% 在教「别动」**；
**35.0% 无论什么模型都只能猜**。这解释了此前每一项观测：
π 学成静止、伪标签退化成先验、macro-recall 恒在随机——**因为训练集本身就是这样分布的**。

**两条排除/澄清**：

- **不是标签错位**：把标签整体平移 −3~+3 帧，冲突率在 shift=0 取最小值
  （33.0 / 33.8 / 34.5 / **35.0** / 35.4 / 37.0 / 37.8%）——单调上升，对得很准。
- **旧数据集是主要噪声源**：逐来源不可辨识占比 —— 我们自己的 CDP 录制
  `house-001/002/003` 是 **10.6 / 23.3 / 32.2%**，而旧项目的人类演示
  `human-001` 的 13 个 episode 是 **25~65%**。⇒ 要用 IDM 就该优先用自己录的那条管线。
- **注意这不是硬上界**：35% 是「只看全局运动幅度」的不可辨识比例；**空间感知**的模型
  原则上能分出一部分（分不开的那部分是**「画面动」到底是世界在动还是我在动」**）——
  这正是差异图探针在找的东西，也是**特权信息路线（读引擎状态）能直接消掉的那一项**。

### 三之二、诚实切分下的真相：**不是「跨场景不泛化」，是「根本没学到映射」**（2026-09-26）

上面那两个数字（45.5% / 91.6%）**来路都有问题**，重测后结论变了：

- **45.5% 来自配置不同的运行**。用同一个探针、同一份数据、同一个种子、同一套超参
  （128px、batch 8、8 epoch、lr 3e-5、best-epoch）重测生产头：**53.1%**（基线 50.4%）。
- **91.6%（同场景内）来自随机划分**。随机划分会把相邻近重复帧分到两侧，是泄漏。
  改成**组内时间序 70/30** 的诚实切分后：

| 条件 | 总体 | 基线 | **运动帧上** | macro-recall |
|---|---|---|---|---|
| 同房间 A/B/C/E/F/G（7 组，均值） | 41.8~82.5% | 46~100% | **0~33%** | 0.09~0.20 |
| 跨房间 A~G（7 组，留出整组） | 40.8~74.4% | 57.8~74.9% | **0~35.6%** | 0.09~0.25 |

**「运动帧上」= 只看真标签非 noop 的留出帧的准确率**——只答 noop 的模型在这里是 0%。
它是「学到映射了吗」的判据，因为总体准确率被 50~100% 的 noop 占比撑着。

**跨房间总体准确率平均低于基线 8.0 个百分点**（7 组：+4.6 / −4.9 / −16.0 / 0 / −7.4 /
−23.2 / −9.4）。**同房间诚实切分也只在基线附近**（−5.0 ~ +2.5）。
**macro-recall 在 0.09~0.25 之间徘徊**，而按类数算的随机水平就在 0.11~0.25 附近。

⇒ **真正的结论是：IDM 在任何测过的配置下都没有学到「按键 → 画面变化」这个映射**，
连同房间、同时间段的诚实切分都学不到。此前把它描述成「跨场景泛化失败」是**把病症
当成了病根**——它连分布内都没学会。这也直接解释了生产里的现象：伪标签退化成先验。

**房间数扫描（留出 E，基线 74.5%；「固定 4000 对」这一列把「房间数」与「数据量」分开）**：

| 训练房间数 k | 不限数据 | 固定 4000 对 | 运动帧上（固定） |
|---|---|---|---|
| 1 | 37.5% | 33.6% | 69.4% |
| 2 | 43.7% | 40.0% | 68.8% |
| 3 | 75.7% | 54.3% | 29.8% |
| 6 | 67.1% | 72.7% | **2.2%** |

固定数据量时总体准确率随房间数**单调上升**（33.6 → 72.7），但**只升到基线附近就停住**；
同时**运动帧准确率从 69.4% 塌到 2.2%**（预测运动的比例 82.4% → 3.2%）。
⇒ **多加房间买到的是「更会押多数类」，不是「更懂动作」。** 这条直接否掉了
「扩覆盖就能救」的读法。

**架构对照（同一份数据、同一种子、同一套超参，4947 对训练 → 4599 对留出，基线 50.4%）**：

| 头 | 总体 | 运动帧上 | macro-recall | 预测运动 |
|---|---|---|---|---|
| 生产头 `[ea, eb, eb−ea]` | 53.1% | **35.2%** | 0.157 | 44.9% |
| 加差异分支 `trunk(\|a−b\|)` | **57.4%** | 30.8% | 0.166 | 35.8% |

差异分支总体 **+4.2 个百分点**，但**运动帧上更差**（30.8% vs 35.2%）、预测运动更少——
**多出来的分是「更会押多数类」，不是「更懂动作」**。
⇒ 架构改动**不是完全没用**（这是唯一一次真正高于基线的改动），但它买到的东西
不是我们需要的那个；而 macro-recall 在所有配置里都没离开 0.1~0.25。

**未测的关键配置（最该补的一次）**：以上全部是**从零训练**（lr 3e-5）。
生产路径另有一条「先用 `pretrain-idm` 在 24k 人类帧上训到 val 0.29，再在循环里微调」，
**这条没有被这次实验覆盖**；而且那个 0.29 是在**随机划分**上量的，按同样的泄漏逻辑
需要重测。要做「IDM 到底行不行」的判决，必须在**同一套诚实切分**下把这条也跑一遍。

**顺带得到一个可复用的正面事实**（探针 `scripts/probe_motion_head.py`）：
「两张图各自全局平均池化后相减」**表达不了运动**（留出 49.0%），
而**把差异图 `\|a−b\|` 直接送进卷积**能学到运动（**留出 85.7%**，甚至高于像素差阈值的 79.2%）。
所以任何需要运动信息的组件都该走差异图，而不是池化向量相减 —— **但运动本身不等于动作**：
从「动了」到「按了哪个键」的映射，跨场景仍然需要标签 ✗。

**后果（机制链）**：

```
IDM 在语料（未见场景）上退化为「答先验」≈ 50% noop
   ↓ π 用 BC 模仿这个分布
π 学成「尽量不动」  ← 观察到；独立测量：20 秒里位置只变 2 次、最后 11 秒完全静止
```

D^R（每轮实际用于训练 π 的检索结果）里**可信数据只占 38%**（合计视频 47 条 / 录制 29 条）；
agent 在小屋时是 4/4 录制（那时标签可信，2.2% noop），一走出覆盖范围就变成 3/4 视频。

## 五、决策记录：接受能力边界（2026-09-26）

**已选定第三条：接受当前能力边界**，停止学习信号方向的实验，把项目定位为
「输入护栏 + 关键时刻记忆 K + 检索」的框架，学习信号部分标注为**待解决**。

**这条决策否定的是「本项目已经实现自进化」这个说法，不是否定管道。** 两边的边界如下。

### 保持成立、可以直接复用的部分

| 能力 | 证据 |
|---|---|
| 三层输入护栏（场景探针 / 后端硬闸 / runner 中止） | 第一节 1，`tests/test_safety.py` 等 223 项测试 |
| 游戏异常场景的自动处置（难度 / 菜单 / 死亡 / 道具弹窗 / 菜单逃生） | 第一节 1，全部真机走过一遍完整链 |
| K：关键时刻发现 + 多轨迹过滤 + 缓存 | 第一节 2，`key_moments 1`、回合 120 → 233 步 |
| 检索：贪心一对一窗口匹配、裁剪后开始选中速通视频 | 第一节 2，余弦 0.8249 → 0.9375 |
| 可观测性：每轮报告（含 `logit_diagnosis` / `pseudo_labels` / `maps`）在 bootstrap 前落盘 | `runs/live*/loop-report.json` |
| 录制：边录边落盘、硬杀可恢复、真实人类按键 | `ash record` / `ash assemble` |

### 不成立、**不要当成已实现**的部分

- **π 不会因为一轮自举而变好**。伪标签是 IDM 在未见场景上的先验（≈50% noop），
  π 用 BC 模仿它 → 学成「尽量不动」。§三的机制链是完整的。
- **K 触发 ≠ 学得到**。K 只是「这里有过关键时刻」，它现在**完全没有进入 π 的更新**——
  论文 Alg 4 的路径是 `K → IDM 打伪标签 → π`，中间那一步是断的。
- **不要用「多录数据」来解决**（已否证，§二 / AGENTS 铁律 8）。
- 因此**不适合把这个项目当作「ASH 复现成功」引用**；适合当作「ASH 的骨架 + 一个
  被测量过的失败点」引用。

### 若要接手学习信号方向：决策时摆出的两条路（原文保留）

1. **修通自监督探针再判断**：诊断判别器为何一步不动（打印 trunk 输出方差）、NaN 来自哪一步。
   判据不变：**跨场景留出准确率必须显著高于多数类基线**。便宜、判据硬。
   入口 `scripts/probe_ssl_idm.py`（**当前是坏的**，见四.1）。
2. **换一条不依赖 IDM 的路**：π 只用 self-play 的**真实动作标签** + K 记忆，不用语料伪标签。
   注意这**会改变论文 Alg 4**，属有意偏差，动手前必须先登记确认。
   这条路唯一被验证有效的进步信号是 **K**（见上表），而现行 π 更新完全没用上它——
   这是最值得改的地方。
